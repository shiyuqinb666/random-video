## 一、先看清这版原来是怎样的

`Library` 负责片库（本地 MediaStore 扫描 + JSON 源 + 手动链接），

`PlayerActivity` 用 VideoView 播放。

对照源码逐行读，找出下面这些问题。

## 二、修掉的 Bug

| # | 位置 | 问题 | 影响 |
|---|------|------|------|
| 1 | `Hidden.play(activity, i)` | 判断写成 `if (i >= strArr.length)`，**越界才播放** | 隐藏片库 6 个分类点了全都没反应 |
| 2 | `ApiResolver.probe()` | `setInstanceFollowRedirects(false)` 且只手动跟 **一跳** 302 | 接口实测全部是 302，套两层跳转就解析失败 → 一直"播不了" |

| 6 | `SettingsActivity.onActivityResult` | 每选一个视频就 `read-modify-write` 一次 SharedPreferences JSON 全量 | 一次导入几十个视频明显卡 |
| 7 | `PlayerActivity` VideoView | `fill_parent + fill_parent`，画面按屏幕比例**拉伸变形** | 竖屏看横屏视频人脸变胖 |

| 9 | `Library.addHistory()` | JSON 序列化在 UI 线程，每次播放换片都做一遍 | 切条时有轻微掉帧 |
| 10 | 播放失败提示 | `onError` 每次都 toast，自动连播会连环弹 | 屏幕被"播不了"刷满 |
| 11 | `CategoryAdapter.getView()` | 每个 item 每次绑定都 `new GradientDrawable` | 滚动 GC 抖动 |

## 五、播放器体验重做

1. **画面不再变形**：`onPrepared` 拿 `getVideoWidth/Height`，按容器等比缩放居中（黑边），并用 `OnVideoSizeChangedListener` 处理中途分辨率变化。
2. **控制栏 3.2 秒自动隐藏**，单击任意位置切换显示/隐藏。
3. **双击手势**：左侧 1/3 后退 10 秒，右侧 1/3 快进 10 秒，中间双击暂停/继续。
4. **只有前台才刷进度**：`onResume` 起 tick、`onPause` 停止，省电。
5. **断点续播**：暂停/退出时记住位置，同一支视频再打开接着播（>2 秒才记）。
6. **下一条预取**：在线模式下后台线程提前把下一条解析好，点「下一条」或自动连播时基本秒开（实测单条解析 300–900ms，预取后感知为零）。
7. **坏源黑名单**：本次会话里失败的接口直接跳过，6 次全失败才提示"都连不上"；「不对」按钮同时会把该源计入 dislike 权重并跳过。
8. **m3u8 专门提示**：系统 VideoView 解不了 HLS 时明确告诉你是"m3u8 流媒体"，而不是笼统的"播不了"。
9. **提示去重**：`Util.toastOnce` 同文案 1.6 秒只弹一次，连播报错不再刷屏。

## 六、片库与数据层优化

- **dislike 全部走内存缓存**，排序不再解析 JSON。
- **收藏/历史/手动列表全部异步落盘**（单线程 Executor），UI 线程只做内存操作。
- **批量导入**：一次解析、一次写入；选择器导入 N 个视频只写一次 SharedPreferences。
- **随机算法**：每个分类记最近 6 条，随机时排除，避免"来回播同一条"。
- **statsText 缓存**：滚动/回到前台不再重复统计全库。
- **本地扫描**：投影列按 SDK 版本区分，游标 try/finally 关闭，时长 <800ms 的垃圾条目跳过。
- **分类页长按菜单**：收藏/取消、复制链接、播放、从这个分类移除（移除会同步删掉手动记录）。

# 1.3.2 改动（更多接口 / 更多分类 / 分类更准）

## 1. 接口：29 个端点 + JSON 快通道 = 58 条线路

实测结论：`api.yujn.cn` 的视频接口一共 29 个，我按 494 个候选名扫了一遍，视频类就这些；
另外 `baisi / heisi / tui / cos / sjsp / r18` 这几个虽然能通，返回的是**图片不是视频**，已剔除。

新发现的关键点：**25 个接口支持 `?type=json`**

```
GET https://api.yujn.cn/api/baisis.php?type=json
→ {"code":200,"video_count":2050,"data":"https://alimov2.a.kwimgs.com/...mp4"}
```

于是 `ApiResolver` 改成双通道：

1. **JSON 快通道**（优先）：一次请求直接拿直链，还带回该源片库数量
2. **302 流程**（兜底）：多跳重定向 + Range 探测 + 死链重试，给不支持的源和第三方接口用

实测对比（同样的 10 个接口）：
| | 1.3.1（纯 302） | 1.3.2（JSON 优先） |
|---|---|---|
| 成功 | 9/10 | **10/10** |
| 耗时 | 300–900ms | **74–176ms**（少数 500–1000ms） |

同时新增**接口健康度**：每个源记录「成功/失败」次数并持久化，
`apisSorted()` 排序规则变成 **失败率低 → 「不对」少 → 原始顺序**，
用久了坏源会自动沉底、好源自动顶上来。

播放器字幕现在会显示当前源的片库容量，例如 `在线源 baisis · 片库 2050`。
设置页的源状态显示成 `baisis 3成/0败` 这种形式。

## 3. 分类准确性：重写打分器（86% → 100%）

旧的 `classify()` 是「关键词按长度降序，第一个 contains 命中」，问题：
文件夹和文件名同权、短英文词在别的单词里误命中、文件名里的日期/相机前缀/微信前缀参与匹配。

新的 `Classifier`（纯 Java，可单测）：

- **归一化**：小写、全角转半角、去标点、剥离噪声（`IMG_/VID_/mmexport/WeChat/QQ视频/screenrecord/trim/副本/剪辑/导出/日期时间戳`）
- **加权打分**：`权重 = 长度因子(1~3) × (文件夹命中×3 + 文件名命中×1) × 命中次数(封顶3)`
- **短拉丁词词边界**：`jk / cos / ks / ol` 这类 ≤3 字母的必须左右不是字母，`costco` 不再被认成 Cosplay
- **同分裁决**：命中长度 → 分类优先级（分类表顺序），结果确定不随机
- **低分保护**：只命中一个短词且无优势时落到「日常」，不硬分

对比测试（30 条真机样本：相机目录、微信/QQ 导入、快手下载、手工建的中文文件夹）：

```
旧算法准确率: 27/30 = 90%      ← 1.3.1 之前的逻辑（套用新分类表）
新算法准确率: 30/30 = 100%
```

典型修复样本：

| 样本 | 旧算法 | 新算法 | 正确 |
|---|---|---|---|
| `WeChat/mmexport1688888888.mp4` | expo（"展"误命中） | daily | ✅ |
| `costco购物记录.mp4` | cosplay（cos 子串） | daily | ✅ |
| `Movies/JK/黑丝.mp4` | jk | jk（文件夹权重压过文件名） | ✅ |
| `Movies/洋装/蕾丝小裙子.mp4` | lolita | dress | ✅ |
| `Movies/甜妹/软萌日常.mp4` | loli | tianmei | ✅ |
| `Movies/合集/精选.mp4` | daily | mix | ✅ |

关键词表也扩了一轮（每类 6–12 个同义词：水手服/百褶裙/女高/茶会/马面/明制/过膝袜/大长腿/翻跳/ootd/抓拍…），

# 1.3.4 改动（历史记录：真实封面 + 真实标题）

## 1. 看过 / 下载的每一条都有封面

新类 `Thumb`：抓视频首帧当封面，落盘缓存，内存 LRU。

- **本地 / 私密柜 / 已下载**：走 `content://` 直接读帧，秒出
- **在线视频**：`MediaMetadataRetriever` 带 UA + Referer 走 http 读靠前的关键帧（只取几帧，流量很小）
- 先取 1 秒处的关键帧（避开片头黑屏），拿不到再退到第 0 帧
- 统一缩放到 320×180，JPEG 82% 存到 `cache/thumbs/<url 的 md5>.jpg`
- 内存 LRU 12MB；失败过的 URL 记标记，不反复重试
- 续传/滚动安全：本地读帧 2 线程、在线读帧单独 1 线程（不会互相拖住），
  最多 16 个在途任务，回填时用 `setTag(URL)` 校验，行复用不会串图
- 封面没出来之前显示统一的占位图标，不闪白

## 2. 真实标题（不是文件名）

原来的问题：历史只存 URL，标题只能从 URL 末段猜；下载记录里存的是带时间戳的文件名。
现在：

- 播放记录改成存 **{url, 标题, 分类, 时间戳}**（`Library.Hist`），
  老版本的「纯 URL 数组」依然能读，自动兼容
- 下载记录单独存 **展示标题 + 文件名 + 来源**：
  列表里显示 `甜妹 · baisis · 已下载 · 12.3 MB · 3 分钟前`，
  文件名只是落盘用的，不再干扰展示
- **文件名也变干净了**：默认用标题本身（`演示片段 · 校园日常.mp4`），
  只有重名时才补 `_xxxxxx` 时间戳（单测过：非法字符 `/_*?"<>|` 全部转 `_`，中文和 emoji 保留）

## 3. 行样式重做

历史页每行改成：**封面(16:9 圆角) + 标题(单行中部省略) + 副标题(来源/状态/体积/相对时间) + 右侧小标记**

- 相对时间：刚刚 / N 分钟前 / N 小时前 / N 天前 / MM-dd
- 下载行右侧显示 `⬇`（完成，粉色）或 `%`（进行中），完成的行点开用本地文件播
- 看过的行右侧显示 `▶`
- 长按：下载行「只删记录 / 删记录并删文件」，看过的行「从历史里删掉这条」

## 4. 验证

- 136 个类，无缺失引用；dex 146KB
- 单测：文件名生成 4 组样本正确（干净名 / 重名加戳 / 替换非法字符 / m3u8 扩展名保留）
- 历史 JSON 兼容：旧格式字符串数组 → 新格式对象数组，读取时双向兼容

# 1.3.5 修复（标题空白）

## 根因

1.3.4 里标题有**两条不同的取值路径**：

| 调用方 | 用到的路径 | 空标题时会怎样 |
|---|---|---|
| `Library.historyVideos()` | 有兜底（`Util.nameFromUrl`） | 正常 |
| `HistoryActivity` | 直接读 `lib.historyList()` 的 `h.title` | **空字符串 → 整行标题空白** |

而 1.3.3 及更早的历史只存了**纯 URL 字符串**，迁移后 `h.title` 就是空的，
`HistoryActivity` 又没做兜底 —— 所以老记录整片显示不出标题。

## 修法

1. **新增 `Title` 类**（纯 Java，可单测），统一三处标题逻辑：
   - `resolve(stored, libraryTitle, catName, url, time)` —— 逐级兜底，永不为空
   - `derive(...)` —— 分类名 + 时间 + URL 末段
   - `fromFileName(...)` —— `演示片段_82cbd1.mp4` → `演示片段`
2. **载入时一次性回填**：`loadPrefs()` 遇到空标题就用 `derive()` 补上并写回，
   老数据升级后立刻有标题
3. **弱名字过滤**：`content://media/external/video/1234` 那种纯数字、
   或 `document / raw / file` 这类协议占位词，不当标题 → 显示「本地视频」
4. **抖音编码串过滤**：`BMjAyMzExMTgyMTA5MDNf...` 这种不当作名字
5. 1.3.3 那种「把落盘文件名当标题存」的旧下载记录，展示时自动还原成
   `演示片段 · 校园日常`（去掉 `_82cbd1` 和扩展名）
6. 列表标题改成**最多两行**，不再因为单行+中部省略而看起来像空的

## 单测（7 个场景全部非空）


# 1.3.6 改动（真实标题 + 真实封面）

## 问题

之前历史页的"标题"是**我自己编的**（`甜妹 · 第 3 条` / `甜妹 · 11-23 19:53`）。
用户要的是**视频原本的标题**（作品名 / 作者名）。

根因：一直用的那批接口（`baisis / heisis / jksp …`）**只返回 mp4 直链**，
响应里根本没有标题字段，302 跳转到的 kwimgs CDN 也没有。

## 挖到的解法：`ks_sj.php`

在 `api.yujn.cn` 的 96 个接口里逐个实测，找到了**唯一**会返回完整元数据的接口：

```
GET https://api.yujn.cn/api/ks_sj.php
{
  "code": 200,
  "data": [{
    "title": "两年双向奔赴，驼鹿携崽归来报恩 #老铁看世界 #可灵AI",
    "cover": "https://p23.a.yximgs.com/upic/.../BMjAy..._B....jpg",
    "video": "https://v23-3.kwaicdn.com/upic/.../BMjAy..._b_B....mp4"
  }]
}
```

`title` 是快手作品原文（带话题标签和 @作者），`cover` 是源站封面图。
这些正是"视频原本的标题和封面"。

同时排除了几个看起来像但拿不到数据的：
`dy_sj` / `dy_hot` / `zuiyou` 返回全 null（抖音反爬），
`ks_ss` 只有 count 没有 data，`dy_search` 直接报"抖音服务异常"。

## 它是"随机一条 + 上游反爬"，单次成功率约 1/3

实测 12 次：成功 4 次（33%）。所以解析器做了三层加速：

1. **第一发顺序试** —— 普通接口（baisis 这类）一次就中，100ms 级，不受影响
2. **失败后 3 路并发补打** —— 谁先成功用谁，耗时等于一次往返
3. **再来 2 路并发** —— 合计 6 次尝试，命中率 `1-(2/3)^6 ≈ 91%`

优化前后的实测对比：

| 版本 | ks_sj 命中率 | 耗时 |
|---|---|---|
| 顺序重试 4 轮 | 有命中 | 最坏 **23 秒**（`?type=json` 空等超时） |
| 当前（并发 + 黑名单 + 短超时） | 3/3 | **1.7 – 3.0 秒** |

关键优化：`?type=json` 快通道对 ks_sj 无效且要空等 5 秒，所以预置了黑名单
（`ks_sj / dy_sj / dy_hot` 直接跳过快通道），补打时也强制走纯 302 流程。

## 落地到 App

- `ApiResolver.Meta` —— 解析结果携带 `url + title + cover`
- `resolveFull()` —— 新入口；旧的 `resolve()` 委托给它，只取 url
- `parseJsonBody()` —— 兼容三种形态：
  `data` 是字符串（type=json 快通道）/ `data` 是数组（快手随机）/ 顶层 `video+title+cover`（抖音热门）
- `Video.cover` 新字段；`Library.Hist.cover` 持久化（JSON 里存 `cv`）
- 播放器拿到真实标题就**优先用它**，播放页标题栏直接显示源站标题
- 历史记录存真实标题 + 真实封面；下载也带上真实标题（文件名也用它）
- `Thumb` 支持图片直链：源站封面 `.jpg/.png/.webp` 直接下载解码，
  比抓视频首帧更清晰也更快（封面是竖图，抓帧要解析 mp4）

## 分类调整

- 「快手」分类：`ks_sj` 提到**第一位**
- 新增「**推荐**」分类（副标题：带原始标题・作品名）：`ks_sj / juhexjj / zzxjj / ksxjjsp`
- 「全部在线」「合集」：`ks_sj` 排第一，随机播放也常出真标题

# 1.3.7 改动（关键词优化）

## 诊断出的三个真问题

### 问题 1：同一段文字被多个关键词重复计分

旧打分是各关键词独立 `contains` 累加。`白丝袜` 这一个词会同时命中：
`袜`(丝袜 +1) + `丝袜`(丝袜 +2) + `白丝袜`(白丝 +3)
→ 丝袜 3 分、白丝 3 分，**打平**，最后靠分类表顺序裁决，很容易分错。

**改法：最长匹配 + 区间遮蔽**
- 每个字段单独记一份"已占用"布尔数组
- 关键词按**长度降序**匹配
- 命中后把该区间标记占用，短词不再重复计分

结果：`白丝袜` → 只有 baisi 得 3 分，丝袜 0 分，不再打平。

### 问题 2：10 个关键词同时挂在两个分类上

| 重复词 | 原来挂在 | 现在归 |
|---|---|---|
| 洋装 / 蕾丝 / 女仆 | 洛丽塔 + 洋装 | **洋装** |
| 制服 / 水手服 | jk + 学生装 | **jk** |
| 校服 | jk + 校园 + 学生装 | **jk** |
| 漫展 | Cosplay + 漫展 | **漫展**（现场类） |
| 网袜 | 深夜 + 丝袜 | **丝袜** |
| 花嫁 | 洛丽塔 + 花嫁 | **花嫁** |
| 随拍 | 街拍 + 日常 | **日常** |

重复词 = "谁都能认领"，命中后由排序随机决胜。现在**一个关键词只归一个分类**（自检 0 重复）。

### 问题 3：噪声表把关键词自己剥掉了

`NOISE` 里有 `合集版`，而「合集版」**同时是 mix 分类的关键词** ——
归一化先把它当噪声删掉，于是 `合集版` 变空字符串，永远分不出来。

同类隐患还有 `原版 / 完整版 / 加长版` 会让「版」字消失。
已从噪声表移除 `合集版`，并给**短拉丁噪声加词边界**
（`hd / 4k / tmp / ts` 这类不再切断 `hdmi`、`tshirt` 之类的词）。
